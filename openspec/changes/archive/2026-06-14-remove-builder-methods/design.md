## Context

All 14 business entity classes (Tenant, Country, State, City, Supplier, Customer, Person, Company, Product, RawMaterial, Warehouse, StockMovement, Sale, SaleItem) were generated by JHipster with fluent builder-style methods for each field. These methods take a field value, delegate to Lombok's `@Setter`, and return `this` for chaining. Production code (`src/main`) does not use these methods — they only appear in test files. The Lombok `@Getter`/`@Setter` annotation on every entity class already generates standard JavaBean accessors.

Product.java has an additional defect: its `@OneToMany` collection `tenants` lacks a custom `setTenants()` method with bidirectional synchronization. The builder method `tenants(Set<Tenant>)` delegates to Lombok's plain setter, which does not clear or set back-references on Tenant objects.

## Goals / Non-Goals

**Goals:**
- Remove all builder-style fluent methods from the 14 entity classes
- Add custom `setTenants(Set<Tenant>)` to Product.java following the existing pattern used by all other entities
- Convert all test files that use builder chaining to standard setter calls
- Preserve add/remove child entity methods and custom bidirectional setters (which have behavior beyond Lombok)

**Non-Goals:**
- Changing any production code behavior or logic
- Modifying entity equals/hashCode/toString methods
- Touching Criteria filter classes (they are separate from entity builders)
- Removing add/remove methods (they synchronize bidirectional relationships)
- Altering any Lombok annotations or field declarations

## Decisions

**1. Remove builder methods entirely vs. deprecating them first**
→ Remove entirely. They are unused in production code and have no callers beyond tests. Deprecation would leave dead code to maintain.

**2. Custom setter pattern for Product's setTenants**
→ Follow the exact same pattern used by Warehouse, Customer, Supplier, Person, Company, RawMaterial, Sale, SaleItem, StockMovement, Country, and State. Iterate old collection to clear back-references, then iterate new collection to set back-references, then assign.

```java
public void setTenants(Set<Tenant> tenants) {
    if (this.tenants != null) {
        this.tenants.forEach(i -> i.setProducts(null));
    }
    if (tenants != null) {
        tenants.forEach(i -> i.setProducts(this));
    }
    this.tenants = tenants;
}
```

**3. Test file conversion strategy: builder chain → sequential setters**
→ Convert each `new Foo().a(x).b(y).c(z)` to:
```java
Foo foo = new Foo();
foo.setA(x);
foo.setB(y);
foo.setC(z);
```
This is mechanical, one-to-one, no logic change.

**4. Which methods to preserve vs. remove**
| Method type | Action | Reason |
|---|---|---|
| `id(Long)` | REMOVE | Duplicates Lombok setter |
| `field(Type)` (simple fields) | REMOVE | Duplicates Lombok setter |
| `collection(Set<X>)` (builder wrappers) | REMOVE | Just delegates to custom setter, add return `this` |
| `addXxx(Xxx)` | KEEP | Synchronizes bidirectional relationship |
| `removeXxx(Xxx)` | KEEP | Synchronizes bidirectional relationship |
| `void setXxx(Set<X>)` (custom bidirectional) | KEEP | Has logic beyond Lombok's generated setter |

## Risks / Trade-offs

- [Test churn] Large number of test files changed (~30 files). Tests remain semantically identical, but git blame shifts.
  → Mitigation: Single commit for the entire change, clear message.

- [Future JHipster regeneration] If entities are regenerated from JDL, builder methods will reappear.
  → Mitigation: This is a rare operation. The JDL (`erp-core.jdl`) is the source of truth for the domain model, not the generated Java files. Document this convention in AGENTS.md.
